## 一、结论

**本次会话中的 `UnknownError`（包含 `cyber_policy`）和 `ContentFilterError`，在 OpenCode 标准消息转换逻辑中都会被跳过，不会作为历史助手消息发送给后续模型。**

因此，不能因为它们仍显示在会话历史中，就认为后续模型会持续读到这些错误，或因为这些错误记录而对后续回答产生偏向。通常也没有必要为了避免这种影响而专门删除或修改这两条错误记录。

但这不保证后续请求一定成功：原来的任务描述、代码、正常工具结果和用户追加的说明，仍可能进入后续上下文，影响回答或再次触发供应商检查。

已核对 OpenCode 官方仓库 **v1.18.30** 标签，对应提交：

文件：`packages/opencode/src/session/message-v2.ts`。

在将历史记录转换为模型消息时，助手消息分支包含以下判断：

```typescript
if (
  msg.info.error &&
  !(
    AbortedError.isInstance(msg.info.error) &&
    msg.parts.some((part) => part.type !== "step-start" && part.type !== "reasoning")
  )
) {
  continue
}
```

这段逻辑的含义是：

1. 助手消息如果有 `info.error`，通常跳过整条消息，不加入后续模型消息列表。
2. 存在一个特定例外：错误属于 `AbortedError`，并且消息中至少有一个不是 `step-start`、也不是 `reasoning` 的片段。这允许某些已产生有效内容的中止消息继续参与后续转换。
3. 本次的 `UnknownError` 和 `ContentFilterError` 都不属于该例外，因此会被跳过。

来源：[OpenCode v1.18.30 消息转换逻辑，第 244–256 行](https://github.com/anomalyco/opencode/blob/v1.18.30/packages/opencode/src/session/message-v2.ts#L244-L256)。

这也说明：**数据库中保存的历史、界面展示的历史和实际发给模型的上下文，并不是完全相同的内容。** 界面保留错误，便于诊断；构造下一次模型请求时，OpenCode 还会进行筛选和转换。

## 四、为什么切换模型后仍可能再次拦截

即使第一条错误记录没有被发送，之前的任务内容仍可能保留在上下文中。后一个模型或其供应商可以根据这些内容独立作出判断。

因此，连续出现两次拦截，只能说明两次请求都没有正常完成，**不能据此认定第二次拦截是由第一条错误记录造成的**。

同时，正常的上下文处理可能涉及压缩、工具结果裁剪、媒体转换和模型切换时的 metadata 处理。不能把完整历史界面直接当作某一次请求的完整输入。

## 五、需要区分的其他情况

### 1. 拒绝内容写在普通助手正文中

如果一条消息没有 `message.error`，只是普通 `text` 中写着：

> 抱歉，我不能帮助完成这个请求。

那么它属于正常助手正文，通常会随历史进入后续上下文。上面的错误过滤规则不会仅凭正文的语义将其排除。

### 2. 用户把错误全文复制进新消息

如果用户把错误提示、错误 JSON 或相关解释复制到一条用户消息里，它们就成为了用户正文，通常会进入后续上下文。

同理，本次“这属于误报……继续吧”的说明属于正常用户消息，可能影响后续模型对上下文的理解。

### 3. 工具执行错误

工具片段的 `state.error` 和整条助手消息的 `message.error` 不是同一个字段。工具错误可能被转换为工具结果发送给模型，用于理解执行失败和决定下一步动作。

因此，不能把“这两条失败助手消息会被排除”扩大解释成“所有错误文本都不会进入模型上下文”。

## 六、缓存 token 不能证明存在负面标签

记录中的“缓存写入”“缓存读取”“输入”“输出”等数值属于用量信息。

大量缓存写入 token 本身不能证明：

- 之前的错误原文被包含在本次请求中；
- 模型给该会话保存了某种负面标签；
- 后续模型因此会改变对用户的态度。

判断模型实际接收到什么，应依据消息转换逻辑或实际请求内容，而不能仅根据 token 数量推断。

## 七、结论的适用范围与不确定性

本分析依据官方 OpenCode 1.18.30 的标准消息转换代码，以及本次会话记录的错误结构。未抓取该会话后续模型调用的实际出站请求。

对于 `makeplay-*` 中转服务是否维护额外的请求历史、风控状态，或自定义插件是否改变消息处理方式，仅凭这些本地记录无法确认。

所以，能够明确说明的是：**标准 OpenCode 逻辑会排除这两条错误助手消息；不能据此进一步保证供应商或中转服务内部完全没有其他状态或处理规则。**

## 八、对当前编辑器使用的建议

对本次这两条已经被标准逻辑排除的错误，通常无需为了避免影响后续回答而专门删除或修改。

查看历史时，可重点区分：

- `message.error`：整条助手消息的失败信息；
- 正常 `text`：通常会进入模型上下文的用户或助手正文；
- 工具片段中的错误：可能作为工具执行反馈进入上下文。

编辑器完整展示这些信息，是为了忠实呈现已有记录，并不意味着展示出来的每个字段都会被发送给模型。
