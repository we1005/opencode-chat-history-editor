# 错误记录对后续模型回答的影响分析

核对日期：2026-09-14 · 对应版本：OpenCode 1.18.30。本文为匿名化的公开说明。

## 问题

会话中出现 `UnknownError`（例如包含供应商的策略拦截代码）或 `ContentFilterError` 后，这些错误是否会作为历史内容影响后续模型回答？

## 结论

**在已核对的 OpenCode 标准消息转换逻辑中，这两类失败的助手消息会被跳过，不会作为历史助手消息发送给后续模型。**

数据库保存的历史、界面展示的历史和实际发送给模型的上下文并不完全相同。错误会保留在界面中用于诊断，但不一定进入下一次请求。

| 示例记录 | 标准转换行为 |
|---|---|
| 助手消息的 `message.error` 为 `UnknownError` | 跳过整条失败的助手消息 |
| 用户随后补充一条正常消息 | 未被压缩、裁剪或其他规则排除时，按用户正文处理 |
| 助手消息的 `message.error` 为 `ContentFilterError` | 跳过整条失败的助手消息 |
| 正常完成的正文、代码、工具调用与结果 | 按正常上下文处理规则保留或转换 |

## 源码依据

官方 `v1.18.30` 标签对应提交 `3104c1428ec91f809e5ab86631300de41eb6952e`，文件 `packages/opencode/src/session/message-v2.ts`：

```typescript
if (
  msg.info.error &&
  !(
    AbortedError.isInstance(msg.info.error) &&
    msg.parts.some((part) => part.type !== "step-start" && part.type !== "reasoning")
  )
) {
  continue
}
```

带 `info.error` 的助手消息通常被排除。例外是特定的 `AbortedError`：消息还存在至少一个不是 `step-start`、也不是 `reasoning` 的片段。`UnknownError` 和 `ContentFilterError` 不属于该例外。

来源：[对应版本第 244–256 行](https://github.com/anomalyco/opencode/blob/v1.18.30/packages/opencode/src/session/message-v2.ts#L244-L256)。

## 为什么后续仍可能出现拦截？

原来的任务描述、代码、正常工具结果及用户补充说明仍可能进入上下文。后一个模型或供应商可以独立判断这些内容。因此，连续出现拦截并不能证明第二次是由第一条错误记录导致。

还需区分：

- **普通助手正文中的拒绝**：如果只是 `text` 写着拒绝内容，没有 `message.error`，通常仍按正常助手正文发送。
- **用户复制粘贴的错误全文**：它已经成为新的用户正文，通常会进入上下文。
- **工具错误**：`part.state.error` 与 `message.error` 不同，可能作为执行反馈传给模型。
- **缓存 token**：属于用量记录，不能据此推断模型给用户或会话留下了负面标签，也不能证明某段错误原文进入了请求。

## 适用范围

本结论来自上述版本源码和记录结构核对，没有抓取实际出站模型请求。中转服务是否维护其他状态、插件是否改变消息转换方式，需要另外验证；不能将此结论扩展成所有版本、所有供应商的保证。

对已经被标准逻辑排除的错误，通常无需为了避免影响后续回答而专门删除或修改。编辑器完整展示错误，是为了忠实呈现已有记录，不代表每个展示字段都会被发送给模型。
