# OpenCode 历史消息编辑器：调研与选型

核对日期：2026-09-14。

## 结论

**在已核对的候选里，基于 KoniKee/opencode-sessions 改造最容易。复用它的会话浏览界面，新增逐 part 编辑器，通过 OpenCode 官方 API 写回。**

已有功能与需求重叠最多：项目 → 会话 → 消息 → part、用户 / Agent 身份、reasoning、工具展示、子会话导航都已具备。主要增加编辑交互与写入服务，不需要继承一个完整的多端 Agent IDE，也不用从零搭建会话 GUI。

这次已按照该结论实现，并用本机 OpenCode 1.18.30 的隔离实例完成真实写回测试。

## 需求边界

目标：选择已有会话，编辑若干历史消息中的用户正文、助手正文、已保存的思考内容，保留后续消息；高级模式支持其他 part 的 JSON。

OpenCode 的模型是 `session → message → part`。一条助手消息可能有多个 reasoning / text / tool 片段。因此不能把 UI 拼接后的整段文字直接覆盖到其中一个 part，否则会丢失片段边界。

### 后端已有正确的数据边界

[`backend/src/services/sessionService.ts`](https://github.com/KoniKee/opencode-sessions/blob/7da596e5656e2c2c496bc8499373fca60a208f32/backend/src/services/sessionService.ts)：

- `getMessageParts()` 保留 `part.id`、`message_id`、`session_id` 和原始 JSON；

[`backend/src/services/db.ts`](https://github.com/KoniKee/opencode-sessions/blob/7da596e5656e2c2c496bc8499373fca60a208f32/backend/src/services/db.ts) 实际使用 `new Database(DB_PATH)` 和 WAL，并非只读连接。部分注释仍写着“只读模式下会失败”，这是注释与实现不一致，不能照搬调研笔记或注释判断功能。

## 为什么使用官方 API 写消息

官方存在：

```http
PATCH /session/:sessionID/message/:messageID/part/:partID?directory=...
Content-Type: application/json

{
  "id": "prt_...",
  "sessionID": "ses_...",
  "messageID": "msg_...",
  "type": "text",
  "text": "修改后的内容"
}
```

请求体是**完整 Part 对象**，不是只传 `{ "text": "..." }`。编辑器先通过 `GET /session/:sessionID/message/:messageID` 获取原 part，再修改需要的字段。

一手依据：

1. [官方 Session API 定义](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/server/routes/instance/httpapi/groups/session.ts)：`updatePart`，OpenAPI identifier 为 `part.update`，请求为 Part schema，支持 directory/workspace 路由。
2. [官方 Session handler](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/server/routes/instance/httpapi/handlers/session.ts)：检查三个 ID 与路径一致，调用 session 的更新服务。
3. [官方 Session 更新实现](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/session/session.ts)：PartUpdated 事件经过正常同步 / 持久化链路。
4. [官方 Server 文档](https://opencode.ai/docs/server/)：headless server、HTTP Basic 认证、OpenAPI 接口。

官方 `dev` 分支目录会演进；本次额外对照了本地源码副本，并以已安装 1.18.30 的真实 HTTP 行为为最终验收依据。

裸 SQL 更新的实现行数更少，但会绕开事件更新路径。这里选择“浏览复用 SQLite，消息编辑走 API”，以尽量保留上游代码并正确写回。

## 实现范围

- 编辑对话框：逐 part 选择、文本、JSON、预览、备份恢复；
- editor routes 和 PartEditor 服务；
- 保存前对照浏览数据库 / API 当前版本，并检查连接实例的会话状态；
- 修改前备份，修改后重新读取 API 核对结果；
- 连接诊断、同源 API 代理、根目录启动与构建命令；
- 修正数据库路径切换后显示仍是旧路径的问题，并支持 XDG_DATA_HOME。

## 验收与边界

服务级测试：7 项通过，覆盖文本 / reasoning、原 metadata 保留、空字符串、无变化保存、版本冲突、生成中会话、ID / 类型校验、API 错误、备份恢复及已删除 part。

隔离的真实 OpenCode 集成测试：用户正文、助手正文、reasoning、tool JSON 均完成编辑 → SQLite 验证 → 冲突拒绝 → 备份恢复。验证 `message` 表以及后续用户消息的整条 part 记录保持原样，并确认编辑与恢复均写入 OpenCode 事件表。

浏览器验证：已完成思考过程文本编辑、保存成功反馈、历史备份载入与恢复；无效 JSON 显示错误且保存按钮禁用。

启动验证：根目录 `dev` 同时启动前后端，同源 Vite 代理能够访问编辑 API；停止根进程后两个子服务端口均已关闭。生产构建与深链接页面加载通过。

这不是数据库事务级别的跨进程 CAS。官方 PATCH 没有暴露 If-Match，独立 OpenCode 进程的运行状态也不共享；编辑时应让目标会话暂停生成。reasoning 签名 / 加密数据由供应商控制，编辑历史文本不保证原签名仍有效。完整说明见 README。
